## 风险与跳过的工作

- [LOW] R1: A literal tab in a path breaks the <entry>\t<reason> protocol (the prompt's 'cannot on POSIX' premise is not strictly correct). — Verified empirically: with ANTHROPIC_CC_DATA_DIR containing a tab, resolve_anthropic_cc_runtime_entry emits '/tmp/verif-ta<TAB>b/.../runtime-entry.js<TAB>' and the parsing at lines 284-285 yields entry='/tmp/verif-ta' (truncated) and reason='b/.../runtime-entry.js<TAB>'. The operators themselves are exactly the specified ${resolved%%$'\t'*} / ${resolved#*$'\t'} and are correct for tab-free paths. POSIX forbids only NUL and '/' in filenames, so tabs are legal. Requires a tab in $ANTHROPIC_CC_DATA_DIR / $XDG_DATA_HOME / $HOME or the npm global root, which no real npm global install path has; discover_targets' five-field IFS=$'\t' read has the same inherent limitation. Not an A1-A9 failure.
- [LOW] R2: An explicitly-specified path gets no launcher durability reminder, in either --check or the menu header. — run_check_mode sets notes=("") when CC_PATCH_EXPLICIT_TARGET=1, and draw_header requires SELECTED_TARGET >= 0 (explicit paths leave it at -1). Confirmed: `./cc-patch-manager.sh <anthropic-cc>/cli.js --check` printed no 注意 line. A6's stated requirement (redirect + reason) is met and A5's discovery-path requirement is met, so I passed both; but a user who pins the runtime entry via a positional arg or CLAUDE_CLI_PATH is not warned that the tree is rebuilt on upgrade — the same 'looks unlocked, actually lost' failure mode this change exists to prevent.
- [MEDIUM] R3: The `cometixcode` real-package acceptance fails, and the cause is a genuine latent tool-side weakness in restore-all — but it predates this candidate. — Confirmed by an independent pristine comparison: `bash tests/test_real_package_acceptance.sh cometixcode` exits 1 with 'FAIL: tree hash mismatch: expected e5f634c0c78a…, got 2ececb902dc4…' on the current working tree AND identically on a pristine `git archive HEAD` extraction in /tmp, so it is not a regression from this candidate. Root cause: the shipped @cometix/claude-code 2.1.284 install carries a stale .cc-patch-manager-baseline (createdAt 2026-09-29) whose snapshots predate the upstream patcher's /*@cc:*/ markers; restoreAllFromBaseline validates only assertBaselineIdentity and assertBaselineMirrors and never compares each managed file's live content against its baseline sha256, so restore writes stale snapshots over live marker-carrying chunks (8 chunk files differ post-restore). It does not affect A9 because that test skips (exit 0) without a target kind. Flagged because restore silently reverting externally-patched code is a real latent defect, just not introduced here.
